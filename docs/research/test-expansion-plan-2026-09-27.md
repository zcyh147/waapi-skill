# WAAPI Skill 测试扩充：第一阶段结论与实施计划

> 本文保留第一阶段审计历史。后续用户已确认：全部纳入的 Agent 案例覆盖 macOS 2022/2025，三个复杂音乐项目优先验证、全部音乐使用 allow 模式，复用 SampleProject 素材、不验播放，并采用 GPT-6 模型预试及历史耗时推导的预算。当前决定以[正式规格](../specs/authoring-integration-expansion.md)为准，不再执行本文旧的代表版本/主机预算。

日期：2026-09-27。审计代码基线：`284899536fc469cecf075643d3942ddc3f98d04e`。

## 先看结论

17 个候选已经逐个与当前公开能力、现有集成案例及 Python 断言核对。建议 **7 个进入正式设计、2 个合并已有题型、4 个先验证能力/验收方式、4 个暂缓**。这是筛选后的设计清单；新 fixture、adapter、oracle 和 profile 还没有实现，当前新增可执行案例为 0。

Python 侧不是覆盖不足就重建：大部分字段已有编译、公开 Gateway 或 verifier 断言，优先复用。确定要补的重点是若干公开业务入口与下层实现之间的衔接，以及新业务案例所需的独立结果验收。

本阶段只新增五份审计/规划文档。没有改 Skill、测试、配置或工程，没有启动 pytest、Wwise、Fresh Agent，也没有重判旧记录。本报告不增加 PASS，不声称全 Skill 每个参数已覆盖。

### 为什么先做三个试点

固定选择 **C01、M01、C06**，与前面对齐的计划一致：

| 试点 | 一个完整业务目标 | 模式与计划交互 | 独立验收 |
| --- | --- | --- | --- |
| C01 | 同一 Voice 只更新指定语言 | ask_before_changes：请求、确认，共 2 turns；1 个业务事务 | 目标素材 hash、另一语言保持、Sound 身份、路由与 Event Target 保持 |
| M01 | 在指定位置建立 Segment/Track 并导入音乐，设置 Track 音量 | allow_changes：明确要求完成修改，1 turn；1 个 import 事务 | 层级、Source、Clip 媒体路径、Track 音量，不能只看空对象 |
| C06 | 更新已有 RTPC 的指定曲线，保留其他曲线 | allow_changes：明确要求完成修改，1 turn；1 个事务 | 更新项 GUID 不变、完整点列、其他 RTPC 集与值保持 |

合计规划为 **3 tasks / 4 user turns / 3 业务事务**，限 2025.1、一个主机、一个固定候选。前置工程与素材由 runner 准备；准备/保存/清理调用另记成本，不能隐藏在“3 个事务”里。语言名、对象身份、控制参数和素材均在题面中明确，避免无意引入澄清 turn。C01 使用工程真实存在的两种语言，中文题面不等于必须新增中文语言包。

这里是拟定用例规格，不是对真实耗时或永远不需澄清的保证。若 fixture 无法满足单事务目标，先修订预算再执行。allow_changes 仍须 Gateway 生成持久的 policy authorization，不能从配置值直接跳过预览或执行前校验。ask_before_changes 的确认必须来自后续用户 turn。

## 2. Python 补充如何落地

测试层次保持三类：程序测试（fake client，不启动 Wwise）、真实 Gateway 测试（Python 经公开入口操作沙盒）、Fresh Agent 集成（自然语言到最终业务）。新 Agent oracle 是测试基础设施工作，不要把它重复计算成另一批新业务案例。

### 优先补公开入口层的具体断言

以下复用现有测试文件及 helper，不建立平行框架：

1. **create 的冲突处理与 replacement owner**：下层已有替换安全测试；公开业务入口需要覆盖 handle→GUID、rename/replace 的完整结果与缺 owner 拒绝。无需复制全部下层漂移矩阵。
2. **object.set 的全局设置**：核对 name_conflict、list_behavior、add_to_source_control 经公开声明到完整请求的映射。逐对象列表模式的测试不自动证明全局设置。
3. **create Action 的时间字段**：已有 set 的 ms→seconds 与 Preview 断言；补 create 的对应公开路径，复用已有时间语义断言。
4. **set 的文件媒体输入**：现有公共入口正例偏重 inline WAV；优先参数化既有用例加入 media-file，而非再开一个同构测试文件。

导入的 source notes/Originals subfolder 在下层已有较强断言，但业务 Adapter 的常用正例只是传入、没有直接核对这两个输出。优先扩充现有断言并核查是否已有其他公共全链测试；不把它报告成“整个系统从未测过”。TSV 的旧版本 checkout、查询 boolean/integer predicate 等保留为小型复核项，确认无现成公开入口断言才补。

### 独立结果验收是另一项工作

- C01 复用现有多语言 hash/身份检查，不重写语言编译器。
- M01 复用 Source/Clip 媒体拓扑读取；单独比较用户请求的 Track 值。
- C06 复用真实 RTPC 生命周期检查；expected values 在 Agent 运行前封存，最终读取独立于其提交的请求。
- Directive 的业务副作用没有完整重建；不能通过放宽强 verifier helper 让 Dialogue/Switch 获得虚假成功。
- 每个 oracle 至少校验目标集合、请求值和明确保持项；只检查 `verified=true` 不足。

实现后按仓库测试阶梯执行：受影响的定向程序测试→固定五版本 Program；harness/contract 大改才扩大 Non-live；随后只运行需要的真实沙盒与 Fresh 试点。具体命令、解释器与固定候选按 `tests/AGENTS.md` 和 semantic README，不在 Skill 环境安装开发依赖。

## 3. 版本与主机：按差异加任务

这是一份建议调度，不是现在就启动全矩阵。代表版本的成功不会被记成其他版本成功。

| 案例 | 首轮主版本 | 第二个 Fresh 版本的建议 | 原因 |
| --- | --- | --- | --- |
| C01 多语言 | 2025.1 | 暂不默认增加 | 五版本语言/身份程序及真实证据优先复用；出现版本差异再展开 |
| C03 同名素材 | 2025.1 | 暂不默认增加 | 重点是精确输入身份及文件路径；跨主机价值高于重复同机制年份 |
| C06 RTPC | 2025.1 | 暂不默认增加 | 先证明 Agent 更新而非创建；2021 不可用边界留在 program/必要 real 层 |
| C08 衰减 | 2025.1 | 暂不默认增加 | 各 lane 曲线编译先走 program；若实际 schema/metadata 改变，追加对应版本 |
| C09 效果器 | 2025.1 | 2022.1 | fixed Effect slot 与后续 EffectSlot 的实际业务拓扑不同 |
| M01 音乐导入 | 2025.1 | 2022.1 | 新旧层级名称及音乐对象发现路径；2021 媒体 accessor 差异先由已有 real/program 验证 |
| M05 Stinger | 2025.1 | 暂不默认增加 | 2023–25 的正向路径；2021/22 不暴露字段的边界不装成正向案例 |

按这份建议，七个主版本案例加两项版本增量，共 **9 个 Fresh 执行单元（单主机）**。这个数字不含未准入的四项、能力阻塞四项、已有案例修订和基础设施重试。若七项都按收窄后的单事务目标设计，C01 ask、其余 allow，则是规划的 **10 user turns / 9 业务事务**；冻结 fixture 后重新核算。

后续 native Windows 优先 C01 和 C03，覆盖中文题面、路径/参数传递、素材身份与不同 Originals 行为。增加两项时为 **11 单元 / 13 turns / 11 业务事务** 的设计预算，而非 17×5×2=170。此选择不是完整 Windows 发布验收；需要正式双主机发布门禁时另立预算。

同一冻结候选的三个试点可计入九单元，不机械再跑一遍。若 Skill、suite、harness、oracle 或不可变选项发生变化，旧试点仍保留原候选证据，不能拼成新候选通过。需要重跑哪些单元由变更影响和证据一致性决定，保留精确 provenance。

## 4. 降低判分误报与耗时成本

当前 Broker 已支持多种无关顺序置换；先复用这些能力。仍存在确切命令数量、序列和部分参数形态限制，新增 profile 需要显式定义可接受的等价操作，不能只声明“以后只看结果”却继续用完全固定脚本评分。

新 profile 的报告应分别记录业务结果、授权/安全、完成状态与效率。可交换的对象集合、独立属性行、JSON key 顺序不作业务差异；有语义的 Playlist/曲线点/依赖顺序仍严格检查。多余但有界、范围内的只读查询可作为效率诊断；绕过 Gateway、未授权写、目标错误、额外修改和不明确写入重试仍是失败。

耗时建议：小任务 2 分钟为软目标，5 分钟检查是否仍有有效进展；超过软目标不会直接判失败。真实 hard timeout 必须在试点前按 host/turn 冻结；目前 harness 的 240/360 秒限制不是自动宽限机制。实现进度分类时要分开模型、Wwise readiness、API 操作、oracle 和清理，不能在运行中的同一冻结 root 随意延长参数。

为避免反复支付 Agent 成本，先用程序测试验证 grader：同业务结果但无关顺序不同应通过；漏对象、重复、改值和顺序敏感变更必须失败。live matcher 与 archive validator 同时验证。现有历史 profile 与 FAIL 保持不变。

**旧 FAIL 不能直接用新 grader 加 `--resume --verify-only` 变成 PASS。** 现有 verify-only 验证的是原冻结证据。若后续开发派生 regrade，需独立输出新审计记录，保留原判定与两版 grader，且原证据确实足够；缺失的执行和回读不能靠重判补出来。本轮不新增这一机制。

## 5. 实施顺序与停止条件

1. 按上述补项扩充现有 Python 断言，完成三个试点的 fixture/独立 oracle/中文题面及精确预算。复核本阶段标为 unresolved 的相关字段，关闭后才给用例准入。
2. 复用正式 campaign/matrix，为新 profile 建立版本化的结果验收与等价策略；先跑程序回归，特别是“接受等价／拒绝错结果”的成对测试。
3. 固定候选、环境、模型与超时后执行三个试点。沿用现有 integration 的低成本模型/设置作为初始选项；如果模型不可用或配置变化，重新记录，不静默替换。
4. 汇总普通失败与耗时；原始失败根封存。只有发现源工程保护、清理或 harness 系统性故障才提前中止整批；单例失败不临时改候选。
5. 试点方法稳定后再扩展其余四个准入案例、两个版本差异和选定 Windows 单元。条件项按收益单独闭合，不自动转成功项。

第一阶段交付的是有代码依据的候选取舍、补项和预算，不是全参数覆盖证书。完成参数全量闭合还需要继续对未纳入本轮的查询长尾、其他 Core、SoundEngine/UI/CLI/Topics 与环境依赖字段建立逐项映射；它们不会因为本报告出现 17 个候选而获得覆盖信用。
